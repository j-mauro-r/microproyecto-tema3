# Sección 3.5 — Integración técnica

> **Nota para el equipo:** este archivo contiene el texto propuesto para la sección 3.5 del reporte Word (`Reporte_Entrega3_final-2.docx`). Revisarlo aquí y pegarlo en el documento una vez acordado.

---

El despliegue local se apoya en dos contenedores Docker independientes coordinados por Docker Compose. El contenedor de la API se construye a partir de `docker/api.Dockerfile`, usando una arquitectura multi-stage sobre `python:3.13-slim`: la primera etapa instala las dependencias en un prefijo aislado y la segunda copia solo los artefactos necesarios, manteniendo la imagen de producción libre de herramientas de compilación. El proceso corre bajo el usuario `appuser` (uid 10001, sin privilegios de root), expone el puerto 8001 y arranca con `uvicorn api.app.functional:app`, que es la aplicación completamente ensamblada con persistencia y orquestación activas. La ruta de la base de datos SQLite se controla mediante la variable de entorno `BIOMAC_DB_PATH`; en ejecución local apunta a `runtime/biomac.db` dentro del contenedor, y en el despliegue sobre AWS ECS ese directorio se sustituye por un volumen EFS propiedad del mismo uid, sin cambios en el Dockerfile.

El contenedor del dashboard se construye a partir del Dockerfile ubicado junto al código fuente en `dashboard_prototipos/dengue-watch-pro/`. Utiliza también una arquitectura multi-stage: la etapa de build corre sobre `oven/bun:1-slim` y genera un servidor Node.js (preset `node-server` de Nitro) mediante `bun run build`; la etapa de producción corre sobre `node:22-slim` con el mismo usuario no privilegiado (uid 10001) y expone el puerto 3000. La URL de la API (`VITE_BIOMAC_API_BASE_URL`) se inyecta como argumento de build y queda incorporada en el bundle estático; el valor local (`http://localhost:8001/api/v2`) debe ser alcanzable tanto desde el navegador del usuario como desde cualquier fetch del proceso Node del dashboard.

Ambos servicios se orquestan mediante `docker-compose.yml` con `network_mode: host`, lo que hace que los puertos 8001 y 3000 queden vinculados directamente a la interfaz de red del host. Esta configuración garantiza que la URL baked-in apunte al mismo endpoint tanto desde el browser como desde el proceso Node, replicando el comportamiento que en AWS logran los dos servicios apuntando al mismo nombre de DNS del ALB. En Railway, la misma configuración de Dockerfiles se mantiene; la plataforma inyecta `VITE_BIOMAC_API_BASE_URL` como variable de entorno en tiempo de build apuntando a la URL pública del servicio de API.

El operador solo necesita tres comandos: `make up` para construir las imágenes y levantar los servicios (incluyendo la instalación automática de Docker si no está presente, vía `.install-biomac.sh`), `make down` para detener los contenedores, y `make delete` para eliminar también las imágenes y volúmenes locales. Los manuales de instalación y usuario, incluidos en `tutorial/`, documentan en detalle cada variante de sistema operativo (Linux nativo, macOS y Windows vía WSL2).
